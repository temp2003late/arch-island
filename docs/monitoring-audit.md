# Аудит моніторингу — 24.10.2026

Висновок: базові обчислення та перевірені сценарії працюють, але називати моніторинг ідеальним або повним не можна. Це перевірка коду, регресійних тестів і коротких запусків на одному комп’ютері, а не доказ безпомилковості на всіх системах.

## Що перевірено

- Загальний CPU: різниці перших восьми лічильників `/proc/stat`; guest не додається вдруге, idle включає iowait. Нульовий інтервал та зменшення лічильників не перетворюються на вигаданий відсоток.
- RAM: `MemTotal − MemAvailable`, перевірка одиниць і меж.
- Мережа: фактичний монотонний інтервал, окрема обробка RX/TX, зникнення інтерфейсу, зміна інтерфейсу й скидання лічильників.
- Процеси: PID + starttime, CPU відносно одного ядра (може перевищувати 100%), RSS, сортування й ліміт 200 рядків. Детальне читання виконується у фоновому потоці лише при відкритій панелі.
- Диск: зайняте місце кореневої файлової системи, не SMART. Кількість процесів: видимі числові каталоги `/proc`, не гарантовано всі процеси хоста в контейнері чи при обмеженнях доступу.

Семантику `/proc` звірено з [документацією ядра Linux](https://docs.kernel.org/filesystems/proc.html). Зокрема, RSS є приблизним показником; точніше читання `smaps` дорожче. У цьому аудиті його не додано.

## Виправлено

1. Alerts міг повідомляти про відсутність проблем, хоча CPU або один напрямок мережі ще не мали валідного інтервалу. Тепер це явно позначено як очікування вимірювання, включно з першим відліком після зміни інтерфейсу.
2. Напис «60 seconds» не відповідав структурі історії: зберігається 60 відліків без часових міток. UI та README тепер чесно описують 60 вимірювань з номінальним секундним інтервалом.
3. Повторний виклик розрахунку CPU процесу міг залишити старе значення при невалідному новому інтервалі або іншому starttime. Результат тепер спершу скидається у «недоступно». Звичайний збір створює свіжі структури, тому це захист допоміжного розрахунку, а не підтверджена постійна помилка UI.
4. Лічильники періодичних операцій тепер обмежені циклом, без необмеженого зростання знакового int.

Додано регресії для початкового стану, недоступної мережі, першого валідного інтервалу після перемикання, очищення історії та повторного розрахунку CPU процесу. Після змін Release-збирання успішне; `ctest --test-dir build --output-on-failure`: 2/2 набори пройшли за 20.80 с. `git diff --check` пройшов.

## Фактична вартість сцени

Використано `scripts/measure-resources.sh` через Wayland з ізольованими налаштуваннями, нічною сценою та закритою панеллю процесів. Запуски послідовні. Вимірювання виконано на бінарнику після оновлення концепту, до невеликих виправлень цього аудиту; код рендерингу в аудиті не змінювався.

| Режим | Інтервал після прогрівання | CPU одного логічного ядра | RSS наприкінці |
| --- | --- | --- | --- |
| Анімований | 20.02 с | 43.96% | 220.07 MiB |
| Reduced motion | 20.01 с | 0.95% | 212.26 MiB |

Це не частка всього багатоядерного CPU. RSS не включає окрему оцінку GPU VRAM. Один короткий запуск кожного режиму не встановлює довгострокові піки, відсутність витоків або поведінку на іншому обладнанні. Активна сцена помітно навантажує систему; оптимізація її CPU є пріоритетом.

## Що залишається

- Метрики CPU/RAM/мережі, перелік PID і запит файлової системи читаються в GUI-потоці. На повільній файловій системі чи за великої кількості процесів можливі затримки UI; потрібне окреме навантажувальне тестування та, за потреби, винесення збору у worker.
- Історія не має часових міток. Після зависання GUI чи сну системи 60 відліків можуть охоплювати більше хвилини. У другому проході додано розрив лінії після паузи понад 2 секунди; повна шкала часових міток і обробка suspend залишаються окремими завданнями.
- У другому проході Automatic навчили стежити за найменшою метрикою активного IPv4 default route. IPv6, policy routing і VPN, що використовує окремі таблиці чи маршрути /1 замість default route, досі не аналізуються.
- Alerts перевіряє доступність основних вимірювань і заповнення `/` від 90%. Температури, GPU, SMART, швидкість дискового I/O та загальний стан здоров’я системи не вимірюються.
- Не виконано тривалого soak-тесту, перевірки suspend/resume, контейнерів, hidepid, hotplug CPU або навантаження десятками тисяч процесів. Тести не доводять абсолютної точності за цих умов.

## Другий прохід — маршрути, паузи, профілювання

Виправлено автоматичний вибір мережі: він тепер перечитує IPv4 default routes на кожному вимірюванні, вибирає найменшу метрику, відкидає неактивні/reject-маршрути й недоступні інтерфейси. Рівні метрики зберігають поточний вибір. Ручний вибір має пріоритет. Це перевірено синтетичними таблицями маршрутів; мережеві налаштування хоста не змінювалися.

Історія позначає розривом інтервал між вимірюваннями понад 2 секунди або немонотонний час. Тест навмисно блокує event loop на 2,3 секунди та перевіряє розрив у CPU/RAM. Зберігається до 60 записів, включно з позначками прогалин; це не точна часова шкала. Окремий тест перевіряє незалежне скидання RX/TX та нерівномірні інтервали.

Опційний діагностичний інструмент:

```sh
cmake --build build --target island-profile -j 4
QT_QPA_PLATFORM=offscreen ./build/island-profile sampling
QT_QPA_PLATFORM=wayland ./build/island-profile baseline
QT_QPA_PLATFORM=wayland ./build/island-profile worldlife
QT_QPA_PLATFORM=wayland ./build/island-profile sailboat
QT_QPA_PLATFORM=wayland ./build/island-profile surface
QT_QPA_PLATFORM=wayland ./build/island-profile signal-lights
```

Інструмент використовує тимчасові налаштування; не входить у звичайне збирання або CTest. `sampling` вимірює 200 створень Monitor із початковим повним збором, включно з диском. На поточному хості: медіана 0,492 мс, p95 0,754 мс, максимум 1,188 мс. Це теплий локальний кеш; результат не виключає затримок на інших файлових системах або при великій кількості процесів. Підстав для негайного великого переписування збору лише за цими вимірами немає.

Усі графічні проби запускалися послідовно через Wayland, нічний режим, 931×980, закрита панель процесів. Після 5 секунд прогрівання CPU процесу вимірюється протягом приблизно 15 секунд:

| Проба до видалення залишкового heat | CPU одного ядра |
| --- | ---: |
| Уся сцена | 43,92% |
| Заморожений час WorldLife | 37,11% |
| Заморожений час вітрильника | 35,03% |
| Заморожений час шейдера поверхні | 43,46% |
| Без рухомих точок світлового маршруту | 39,50% |

Це окремі короткі проби, а не адитивна розбивка CPU. Замороження часу шейдера не прибирає сам шейдер із рендерингу, тому таблиця не вимірює його GPU-вартість. Найпомітніша різниця серед перевірених заморожень — у вітрильника та WorldLife. Потрібні повторні проби перед зміною якості анімацій.

Додатково видалено невикористану властивість `heat`, її анімацію та shader uniform, які залишилися після видалення вулкана. Це усуває зайві оновлення стану без зміни видимого ефекту.

Двохвилинна перевірка перед змінами другого проходу: RSS на 15/45/75/105 с становив 213,88 / 214,52 / 214,44 / 214,35 MiB. Стійкого зростання в цьому вікні немає, але це не тест на відсутність витоків протягом годин. Під час частини цього запуску виконувалось збирання, тому його CPU-лічильники не використовуються для порівняння компонентів.

Після видалення залишкового `heat` повторено повну сцену двічі за тих самих умов: **34,54%** і **34,78%** одного ядра проти попередніх **43,92%**. Локально це приблизно на 21% менше CPU процесу; це не FPS-метрика і не гарантія однакового виграшу на іншому GPU/драйвері. Візуальна деталізація й частота годинника сцени не знижувалися.

Фінальна перевірка другого проходу: збирання основного бінарника, обох тестових бінарників і опційного профайлера успішне. CTest: 2/2 набори пройшли за 23,86 с. `islandInteraction` на Wayland/GPU: пройшов за 11,36 с, включно з рухом води, стабільністю даху, зупинкою сцени, панелями та малим розміром. У цьому запуску вимкнено лише відомі попередження категорії `qt.qpa.wayland.textinput`; збір QML-помилок тестом залишався ввімкненим. `git diff --check` пройшов.
